## 1. 背景

广场由统一 `posts` 表 + `post_type`（announcement / feedback / courtyard）承载，目前**无任何回复 / 留言能力**。本期为反馈墙补「管理员单条回复」，为大院补「用户顶层匿名留言」，并新增「我的帖子被回复」轮询通知接口。公告墙不参与。

技术栈：Express + `mysql2/promise` 原生 SQL（无 Drizzle），迁移走 `migrations/*.sql`，分层为 `routes.ts` + `repo.ts`。

## 2. 目标

1. 新增 `post_replies` 表，统一承载「反馈墙管理员回复」与「大院用户留言」。
2. App 端：帖子详情附带回复 / 留言；大院留言创建与删除；「我的帖子新回复」轮询接口（含通知置位）。
3. Admin 端：反馈墙单条回复增删改；大院留言单独删除；删帖连带删回复；全站帖子详情含实名留言。
4. 鉴权与软删规则与既有 posts 模块一致；SQL 全参数化；多步写操作走事务。

## 3. 边界（非目标）

- 不做嵌套回复（楼中楼）；不设 `parent_reply_id`。
- 不做管理员回复操作留痕（不记录修改人 / 修改时间）。
- 不做公告墙回复 / 留言（`post_type=announcement` 一律拒绝）。
- 不做点赞、举报、富文本、图片。
- 不做推送通知（仅前台轮询）。
- 不做留言数量上限约束；仅做内容长度上限。
- 不引入 Drizzle / ORM；不新建独立 service 层（`repo.ts` 过大则拆 `postReplies.repo.ts`）。

## 4. 数据模型

### 4.1 新表 `post_replies`

用 `kind` 区分两种语义（与 `posts.post_type` 设计风格一致）：

| 字段              | 类型        | 约束                                            | 说明                                           |
| ----------------- | ----------- | ----------------------------------------------- | ---------------------------------------------- |
| `id`              | BIGINT      | PK, AUTO_INCREMENT                              |                                                |
| `post_id`         | BIGINT      | NOT NULL, FK → posts.id                         | 关联帖子                                       |
| `kind`            | VARCHAR(16) | NOT NULL, CHECK IN ('admin_reply','comment')    | admin_reply=反馈墙管理员回复；comment=大院留言 |
| `author_user_id`  | BIGINT      | NOT NULL, FK → users.id                         | 留言者 / 回复管理员（管理端实名用）            |
| `content`         | MEDIUMTEXT  | NOT NULL                                        | 纯文本                                         |
| `notified_author` | TINYINT(1)  | NOT NULL DEFAULT 0                              | 是否已通知帖子作者（0=待通知）                 |
| `deleted_at`      | DATETIME(3) | NULL                                            | 软删                                           |
| `created_at`      | DATETIME(3) | NOT NULL DEFAULT CURRENT_TIMESTAMP(3)           |                                                |
| `updated_at`      | DATETIME(3) | NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE |                                                |

索引：

- `KEY idx_replies_post_kind_created (post_id, kind, created_at)` — 列表主索引
- `KEY idx_replies_author_created (author_user_id, created_at)` — 备用
- `KEY idx_replies_notified (notified_author, post_id)` — 轮询新回复用

外键：

- `FK post_replies.post_id → posts.id ON DELETE CASCADE`（DB 级硬删兜底；应用层走软删级联）
- `FK post_replies.author_user_id → users.id`

### 4.2 「反馈墙单条回复」约束

- `kind='admin_reply'` 与 `post_id` 满足「每帖至多一条未删除回复」。
- MySQL 不支持部分唯一索引，采用**应用层事务内校验**：
  - 创建：事务内 `SELECT ... WHERE post_id=? AND kind='admin_reply' AND deleted_at IS NULL FOR UPDATE`，存在则 409；否则 INSERT。
  - 更新：同上锁行，存在则 UPDATE，不存在则 404。
  - 删除：定位行，软删 `deleted_at`。
- 软删后允许再次创建（新行），满足「删了可再回」。

### 4.3 `notified_author` 语义

- 新建 `admin_reply` / `comment` 时 `notified_author=0`。
- 仅当回复的 `post.author_user_id` 为当前轮询用户时，该回复进入「我的新回复」通知流。
- 轮询接口返回这些 `notified_author=0` 的回复后，**同事务内置位为 1**，每条只触发一次 toast。
- 帖子被软删后其下回复随帖子软删，不再进入通知流（列表层已过滤）。

### 4.4 级联删除

- 管理员删任意帖（`DELETE /api/admin/posts/:id`，既有软删）时，**同事务内**将该帖下所有 `post_replies` 软删，无论 `kind`。
- 用户删自己的帖子（`DELETE /api/app/posts/:id`）同样级联软删其下回复（含他人留言）。
- 用户删自己的留言仅软删该条 `comment`，不影响帖子与其他留言。
- DB 级 `ON DELETE CASCADE` 仅作硬删兜底（正常路径不触发）。

### 4.5 迁移文件

新增 `apps/nongyu-node-server/migrations/009_post_replies.sql`：建表 + 索引 + 外键 + CHECK。不改 `posts` / `post_reads`。同步更新 `docs/nongyu-node-server/数据库设计文档.md`。

## 5. API 契约

### 5.1 App 端

#### 5.1.1 `GET /api/app/posts/:id`（扩展）

既有字段不变，按 `post_type` 分支新增：

- `feedback`：新增 `adminReply: { content: string, publishedAt: string } | null`
  - `publishedAt` 取 `post_replies.created_at`；不返回作者任何信息（用户侧统一「管理员回复」）。
  - 仅未软删的 `admin_reply`（至多一条）。
- `courtyard`：新增 `comments: Array<{ id: number, content: string, publishedAt: string, isMine: boolean }>`
  - 按 `created_at ASC`；仅未软删的 `comment`。
  - `isMine = (comment.author_user_id === 当前用户 id)`；不返回作者其他信息。
- `announcement`：不新增字段（`adminReply=null`、`comments=[]` 可不返回或返回空，保持兼容）。

鉴权、计阅读、帖子维度 `isMine` 逻辑不变。

#### 5.1.2 `POST /api/app/posts/:id/comments`（新建）

- 用途：大院帖子下发表匿名留言。
- 鉴权：App JWT（用户）。
- Body：`{ content: string }`，trim 后长度 **1–1000**；否则 400，`code: 40001`。
- 业务规则：
  - 帖子必须存在且 `post_type='courtyard'` 且未软删；否则 404 / 400（`code: 40002` 非大院帖不可留言）。
  - 不允许对 `announcement` / `feedback` 留言。
  - 不做单帖留言数量上限。
- 成功 `data`：`{ id: number, publishedAt: string }`，HTTP 201。
- 副作用：`notified_author=0`（待通知帖子作者）。

#### 5.1.3 `DELETE /api/app/posts/:id/comments/:commentId`（新建）

- 用途：用户删除自己的大院留言。
- 鉴权：App JWT（用户）。
- 业务规则：
  - 留言必须存在、`kind='comment'`、未软删、`author_user_id === 当前用户`；否则 403 / 404。
  - 软删该条 `post_replies.deleted_at`。
- 成功 `data`：`{ id: commentId }`，HTTP 200。
- 非本人留言不可删（管理员删除走 admin API）。

#### 5.1.4 `GET /api/app/users/me/post-replies/new`（新建，轮询用）

- 用途：轮询「我的帖子是否有新回复」，返回未通知的回复并置位。
- 鉴权：App JWT（用户）。
- 无 Query 参数。
- 行为（单事务）：
  1. 查询：连接 `post_replies` 与 `posts`，过滤 `p.author_user_id = 当前用户`、`r.notified_author = 0`、双方均未软删，按 `r.created_at ASC`，`LIMIT 50`。
  2. 将这些 `r.id` 的 `notified_author` 置 1。
  3. 返回列表。
- 成功 `data`：`Array<{ replyId: number, postId: number, postType: PostType, postTitle: string, kind: 'admin_reply'|'comment', content: string, createdAt: string }>`
  - `kind='admin_reply'` 时客户端 toast：「你的反馈帖《标题》已被管理员回复」。
  - `kind='comment'` 时 toast：「你的大院帖《标题》收到新留言」。
- 单次最多返回 50 条；超过 50 条未通知时，分批置位，客户端下次轮询继续取剩余。
- 客户端 30s 轮询；服务端可加软限流（非本期硬性）。

### 5.2 Admin 端

#### 5.2.1 `POST /api/admin/posts/:id/reply`（新建）

- 用途：对反馈墙帖子创建管理员回复（单条）。
- 鉴权：Admin JWT。
- Body：`{ content: string }`，trim 后长度 **1–2000**；否则 400，`code: 40001`。
- 业务规则：
  - 帖子必须存在且 `post_type='feedback'` 且未软删；否则 404 / 400（`code: 40002`）。
  - 事务内 `SELECT ... FOR UPDATE` 校验无未软删 `admin_reply`；存在则 409（`code: 40901`，提示「该帖已有回复，请改用更新」）。
  - INSERT `post_replies (post_id, kind='admin_reply', author_user_id=当前管理员, content, notified_author=0)`。
- 成功 `data`：`{ id: number, content: string, publishedAt: string }`，HTTP 201。

#### 5.2.2 `PATCH /api/admin/posts/:id/reply`（新建）

- 用途：更新该反馈帖的现有管理员回复。
- 鉴权：Admin JWT。
- Body：`{ content: string }`，长度同 §5.2.1。
- 业务规则：
  - 帖子须 `post_type='feedback'` 且未软删。
  - 事务内 `SELECT ... FOR UPDATE` 定位未软删 `admin_reply`；不存在则 404（`code: 40404`）。
  - UPDATE `content`、`updated_at`；**不重置 `notified_author`**（已通知的不重复通知；未通知的保持未通知，下次轮询通知）。
- 成功 `data`：`{ id, content, publishedAt }`，HTTP 200。

#### 5.2.3 `DELETE /api/admin/posts/:id/reply`（新建）

- 用途：删除该反馈帖的管理员回复。
- 鉴权：Admin JWT。
- 业务规则：定位未软删 `admin_reply`，不存在 404；软删 `deleted_at`。
- 成功 `data`：`{ id }`，HTTP 200。

#### 5.2.4 `DELETE /api/admin/posts/:id/comments/:commentId`（新建）

- 用途：管理员单独删除任意大院留言（不删帖）。
- 鉴权：Admin JWT。
- 业务规则：留言须 `kind='comment'` 且未软删；软删。不存在 404。
- 成功 `data`：`{ id: commentId }`。

#### 5.2.5 `DELETE /api/admin/posts/:id`（扩展）

- 既有软删帖逻辑基础上，**同事务内**软删该帖下所有 `post_replies`（§4.4）。

#### 5.2.6 `GET /api/admin/posts/:id`（扩展）

- 既有返回基础上新增：
  - `adminReply: { id, content, publishedAt, updatedAt, authorUserId, authorStudentNo, authorName } | null`（实名）。
  - `comments: Array<{ id, content, publishedAt, authorUserId, authorStudentNo, authorName }>`（实名，按 `created_at ASC`）。
- 仅未软删的回复 / 留言。

#### 5.2.7 `GET /api/admin/posts`（扩展，可选）

- 列表项新增 `replyCount: number`（未软删回复总数，含 `admin_reply` 与 `comment`）；便于管理端列表展示角标。
- 其余字段与分页不变。

### 5.3 `DELETE /api/app/posts/:id`（扩展）

- 用户删自己帖子时，**同事务内**级联软删其下 `post_replies`（§4.4）。

## 6. 错误码

新增（避免与既有 `ErrorCodes` 冲突）：

| code  | HTTP | 含义                      | 常量名建议              |
| ----- | ---- | ------------------------- | ----------------------- |
| 40002 | 400  | 该 post_type 不支持该操作 | `POST_TYPE_NOT_ALLOWED` |
| 40304 | 403  | 非本人留言不可删          | `COMMENT_NOT_OWNED`     |
| 40404 | 404  | 管理员回复不存在          | `POST_REPLY_NOT_FOUND`  |
| 40405 | 404  | 留言不存在                | `COMMENT_NOT_FOUND`     |
| 40901 | 409  | 该帖已有管理员回复        | `POST_REPLY_EXISTS`     |

注：既有 `40301=ACCOUNT_DISABLED`、`40401=USER_NOT_FOUND`、`40402=POST_NOT_FOUND`，新增码避开。

## 7. 业务流程

### 7.1 大院留言

```
用户进大院帖详情 → GET posts/:id（含 comments）
  → 输入留言 → POST posts/:id/comments → 201
  → 列表追加新留言（isMine=true）
  → 删自己留言 → DELETE posts/:id/comments/:commentId → 软删
```

### 7.2 反馈墙管理员回复

```
管理员在管理端选反馈帖 → POST admin/posts/:id/reply
  → 201（无则创建）/ 409（已有则改用 PATCH）
  → 编辑 → PATCH admin/posts/:id/reply
  → 删除 → DELETE admin/posts/:id/reply
用户进自己反馈帖详情 → GET app/posts/:id（adminReply 非空）
```

### 7.3 我的帖子新回复轮询

```
App 前台 30s → GET app/users/me/post-replies/new
  → 返回未通知回复列表 + 同事务置位 notified_author=1
  → 客户端对每条 toast
```

### 7.4 删帖级联

```
管理员/用户删帖 → 软删 posts.deleted_at + 同事务软删该帖 post_replies.deleted_at
```

## 9. 决策记录（grill 结论）

| 项             | 结论                                                               |
| -------------- | ------------------------------------------------------------------ |
| 需求分类       | 业务需求                                                           |
| 表设计         | 统一 `post_replies` + `kind` 区分（与 `posts.post_type` 风格一致） |
| 单条回复约束   | 应用层事务内 `SELECT ... FOR UPDATE` 校验（MySQL 无部分唯一索引）  |
| 通知判定       | `notified_author` 标记，轮询返回后同事务置位                       |
| 级联删除       | 软删级联（应用层事务），DB FK CASCADE 仅硬删兜底                   |
| 管理员回复身份 | 用户侧统一「管理员回复」，不暴露具体管理员；管理端实名             |
| 大院留言匿名   | 完全匿名，仅 `isMine` 自识；管理端实名                             |
| 留言层级       | 仅顶层，不嵌套                                                     |
| 内容长度       | comment 1–1000；admin_reply 1–2000                                 |
