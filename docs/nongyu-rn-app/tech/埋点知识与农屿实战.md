## 1. 埋点是什么？

埋点是为数据分析服务的，它决定了分析所用的**数据本身**：分析侧读到的指标与明细，来源于客户端（及少量服务端）的**采集与上报**。

没有可靠埋点，产品决策、体验优化、性能与稳定性治理都会缺少事实依据。

---

## 2. 埋点的意义以及对应的采集方向

| 意义                                 | 典型采集方向                     |
| ------------------------------------ | -------------------------------- |
| 分析用户行为，支撑产品决策与体验优化 | 页面事件、点击事件、曝光事件     |
| 识别性能瓶颈并优化                   | 性能指标（首屏、关键路径耗时等） |
| 收集报错与崩溃，提升稳定性           | 报错 / 崩溃信息                  |

农屿一期**不做曝光事件**；行为侧以页面浏览 + 重点点击为主，性能与 JS 报错按需接入。

---

## 3. 埋点的两大注意点

1. **采集的正确性**：用正确手段采到正确字段与指标（例如停留只计前台可见时长，而不是墙钟时间）。
2. **上报的完整性**：重点是少漏报——处理杀进程、弱网、登出清 Token 前最后一批等边界。

---

## 4. 埋点技术的分类（前端）

| 类型                     | 做法概要                            | 优劣简述                                 |
| ------------------------ | ----------------------------------- | ---------------------------------------- |
| **手动埋点**（代码埋点） | 封装 `track`，在业务处显式调用      | 灵活精准；依赖人工，易漏、难维护         |
| **无埋点**（全埋点）     | 顶层引入一次 SDK，全局自动采集      | 省人力；量大、难控、易污染数据、更吃性能 |
| **可视化埋点**           | 基建就绪后，运营/分析在端内圈选配置 | 业务可直达配置；基建复杂度最高           |
| **混合埋点**             | 多种技术组合                        | 实际业务最常见                           |

农屿一期是**混合**：页面浏览走「类无埋点」自动采集，点击与性能走手动埋点。

## 5. 埋点的数据特征与数据库选型（后端）

### 5.1 数据特征（相对业务 OLTP）

| 特征         | 含义（埋点侧）                                                       |
| ------------ | -------------------------------------------------------------------- |
| 写入为主     | App 批量 POST，日事件量通常远大于业务表写量                          |
| 追加型       | 事件一旦入库极少改写；靠幂等键防重复                                 |
| 明细短命     | 原始行用于排查与重算；长期看趋势更依赖聚合                           |
| 查询偏分析   | 大屏要的是 DAU、频次分布、性能分位、崩溃趋势，不是单行事务一致性热点 |
| 与账号弱耦合 | 事件带 `user_id`（服务端从 JWT 解析），但不宜与业务核心表同库抢资源  |

### 5.2 业界常见选型对照

| 方案               | 适用场景                     | 代价                        |
| ------------------ | ---------------------------- | --------------------------- |
| 业务 MySQL 同库    | 量极小、临时验证             | 分析查询拖慢 OLTP；磁盘膨胀 |
| 独立 MySQL / PG    | 中等规模、要 SQL 生态        | 运维多一套库                |
| ClickHouse 等 OLAP | 大规模明细 + 复杂分析        | 运维与成本高，小体量过重    |
| 嵌入式 SQLite      | 单实例、日事件可控、部署极简 | 水平扩展弱；写需串行化      |
| 商用 SaaS          | 要开箱分析与看板             | 费用、数据出境/私有化约束   |

### 5.3 农屿选型（一期 as-built）

| 项       | 结论                                                                            |
| -------- | ------------------------------------------------------------------------------- |
| 服务     | 独立 `nongyu-go-track-server`（Go）                                             |
| 存储     | **嵌入式 SQLite**（WAL + 单 writer），**不进**业务 MySQL                        |
| 分层     | L0 `events` 原始约 30 天；L1 日聚合约 400 天；L2 `user_presence` 辅助在线       |
| 幂等     | 客户端 `event_id`（UUID）；失败重试不换 ID                                      |
| 在线态   | Track 收心跳后**回写** Node → MySQL `users.is_online`；大屏「当前在线」读业务库 |
| 升级触发 | 日事件持续 ≫ 50 万、大屏查询长期变慢、或需多实例写扩展时再议独立 MySQL / OLAP   |

容量粗估与表设计见 Track 技术方案；本文只固定「为何与业务库拆分、为何一期 SQLite 够用」。

## 6. 业内埋点方案调研

| 路线                             | 说明                                | 农屿态度                                      |
| -------------------------------- | ----------------------------------- | --------------------------------------------- |
| 接商用 SDK（神策、友盟、火山等） | SaaS 或私有化，采集→存储→分析全链路 | **一期禁止**；自研可控、成本与数据在自己侧    |
| 基于开源二开（如 Sentry）        | 强项在性能与报错；用户行为能力弱    | 可作崩溃参考，不替代行为埋点                  |
| 全栈自研（如小米 oneTrack）      | 采集 SDK + 接入服务 + 分析查询      | **农屿路线**：RN 模块 + Go Track + Admin 查询 |

## 7. 埋点原理概览（以 Web 为例）

便于对照理解；农屿端是 React Native，对应实现见 §9。

### 7.1 点击事件

- 手动：业务处调 `track`。
- 或事件委托：根节点监听，子节点 DOM 上挂标识与参数。

### 7.2 页面事件

区分 SPA / MPA；本质是监听 URL（或路由）变化。Hash / History 差异只影响监听点。

### 7.3 曝光事件

现代标准：`IntersectionObserver`；常配合可视面积与停留阈值过滤「快速划过」。

### 7.4 性能事件

浏览器 **Performance API** 体系（导航、资源、自定义 mark/measure 等）。

### 7.5 报错事件

| 类型               | 常见手段                           |
| ------------------ | ---------------------------------- |
| JS 同步运行时错误  | `window.onerror`                   |
| Promise 未处理拒绝 | `unhandledrejection`               |
| 静态资源加载失败   | 捕获阶段 `error`（资源错误不冒泡） |
| 接口异常           | 劫持 `XMLHttpRequest` / `fetch`    |

## 8. 埋点需求的场景问题与解决方案（以 Web 为例）

### 8.1 漏报

用户关 Tab / 杀进程、弱网失败未补发。

- **网络**：页面卸载后普通 XHR/fetch 易被打断 → 优先 `navigator.sendBeacon`，或 `fetch` + `keepalive`。
- **机制**：未上报队列持久化，下次进入再发；切后台时及时 flush，降低「挂后台再直接杀掉」的丢失面。

### 8.2 错报

- **停留时间**：`visibilitychange` / `document.hidden` 时暂停计时。
- **曝光**：可视面积 + 停留超过阈值才算有效曝光。
- **PV**：防抖；路由事件需真正 path 变化。
- **点击**：关键按钮可防抖，避免连点刷量。

### 8.3 影响业务性能

- SDK 异步加载 / 代码分割；队列批量上报与去重；避免主线程重计算，上报可以使用requestIdleCallback。

### 8.4 侵入性

无埋点侵入小、代码埋点侵入大；混合方案在关键路径用显式 API，生命周期用宿主组件收敛。

## 9. 农屿埋点实战

### 9.1 确认埋点需求

**采集（一期）**

| 方向     | 范围                                                                                                       |
| -------- | ---------------------------------------------------------------------------------------------------------- |
| 用户行为 | 点击 + 页面浏览（含可见停留）；**不做**曝光                                                                |
| 性能     | 个别页面；当前主要是课表周视图首屏 `course_week_first_paint`                                               |
| 报错     | JS（`ErrorUtils`）+ 根 ErrorBoundary + 未处理 Promise + 农屿 `appFetch`/`appAuth`；不做原生崩溃 / 商用 APM |

**分析与查看**

| 能力           | 说明                                                                    |
| -------------- | ----------------------------------------------------------------------- |
| Web 管理端大屏 | 多图表展示日活、页面/按钮、性能分位、崩溃等（读 Track 聚合 + 业务在线） |
| 智慧助手问数   | 管理端智能问数（能力分期落地，与埋点数据同源）                          |

### 9.2 确认埋点环境

- **埋**：`apps/nongyu-rn-app`（用户真实使用面）。
- **不埋**：Web 管理端——对内、用户量小，行为埋点收益低。
- **存与查**：`nongyu-go-track-server`；Admin 经 Node BFF 查 Track，不暴露 Track 给公网随意访问。

### 9.3 埋点方案选型（采集侧）

| 事件类型    | 农屿一期方案                     | 实现要点                                                                         |
| ----------- | -------------------------------- | -------------------------------------------------------------------------------- |
| 点击事件    | **手动埋点**                     | `trackClick(eventName)`；**未做**可追踪 HOC / 高阶按钮（选型曾提过，一期未落地） |
| 页面事件    | **类无埋点**                     | `TelemetryHost` 监听 Expo Router `pathname`；enter/leave + 可见停留              |
| 性能事件    | **手动埋点**                     | `track({ event_type: "perf", ... })` 或 `measure` / `measureAsync`               |
| 报错事件    | **全局钩子 + Boundary + 请求层** | `installCrashTracking` + `AppErrorBoundary` + `reportAppRequestError`            |
| 会话 / 在线 | Host 驱动                        | `app_open`、60s `heartbeat`；登出 `shutdownForLogout` + offline                  |

代码目录：`apps/nongyu-rn-app/src/modules/telemetry/`。

### 9.4 点击事件（手动）

```text
业务 onPress → trackClick("stable_english_name") → enqueue → MMKV → flush → Track
```

一期已接线示例：

| 场景     | event_name                                                          |
| -------- | ------------------------------------------------------------------- |
| 底栏 Tab | `tab_home` / `tab_course` / `tab_center` / `tab_mine`               |
| 农屿 AI  | `nongyu_ai`                                                         |
| 首页入口 | `entry_jiaowu` / `entry_second` 等（`entry_${key}`）                |
| 登出     | `logout`（须在清 Token **之前**，见下）                             |
| 分享     | `share_open` / `share_wechat` / `share_moments` / `share_copy_link` |

约定：`event_name` 用稳定英文蛇形/下划线名，便于聚合；敏感键不会进 `props`（client 侧黑名单过滤）。

### 9.5 页面事件（自动 + 可见停留）

```text
登录且 hydrated
  → app_open（cold_start / session_start）
  → pathname 变化：上一页 leave（带 duration_ms）→ 本页 enter
  → AppState background：leave(reason=background) 停表保留 path；回前台续计，不重复 enter
  → duration_ms < 300ms 的 leave 不上报（滤瞬时跳转 / Strict Mode 噪音）
  → /login 不追踪；进登录页会结算上一页
```

对应 Web 的「路由监听 + visibility 校准」：RN 用 `usePathname` + `AppState`，逻辑在 `screenDwell.ts`。

后台**仍发心跳**（产品：挂后台仍算在线）；**页面停留只计前台可见时长**。

### 9.6 性能事件

| API                                                             | 用途                            | 一期业务使用情况                                     |
| --------------------------------------------------------------- | ------------------------------- | ---------------------------------------------------- |
| `track({ event_type: "perf", event_name, duration_ms, props })` | 调用方自己掐表                  | **课表**：`course_week_first_paint`（当前周 layout） |
| `measure(name, fn)`                                             | 同步段自动记 `duration_ms`      | 基建已实现，业务侧尚无调用点                         |
| `measureAsync(name, fn)`                                        | 异步段同上，返回原 Promise 结果 | 基建已实现，业务侧尚无调用点                         |

课表约束（避免脏耗时）：peer 模式 / loading / error 时不报；`props` 可带 `week_index`、`max_week`。

### 9.7 报错事件

```text
app/_layout 模块加载时 installCrashTracking()
  → ErrorUtils.setGlobalHandler → crash fatal|js
  → Hermes Promise tracker → crash unhandled_rejection
  → enqueue + void flushPending；保留原 handler / 不阻断

根 AppErrorBoundary
  → componentDidCatch → crash react（+ component_stack）→ 降级「重试」

appFetch / appAuth / parseApiResponse
  → crash network|api（method/path/code；60s 降噪）→ 仍 throw
```

边界：

- **有**：全局 JS、根 React Boundary、未处理 Promise、农屿 Node 请求失败。
- **无**：原生崩溃、教务/二课请求、Track transport 失败二次埋点、多层 Boundary。

采集路径自身再抛会死循环，故整段 try/catch 吞掉。

### 9.8 上报完整性与正确性（对照 §8，落在 RN）

| Web 问题        | 农屿做法                                                                   |
| --------------- | -------------------------------------------------------------------------- |
| 卸载丢包        | 无 `sendBeacon`；靠 **MMKV 持久队列** + 下次登录后 flush；批失败原包回队头 |
| 弱网漏报        | NetInfo 未连接则只积压不发；恢复后 Host 定时 / 心跳触发 flush              |
| 登出丢最后一批  | `shutdownForLogout`：先结算 leave → flush → offline，**再**清 Token        |
| 停留错报        | 后台 settle 停表；回前台 `resumeScreenDwell`；过短 leave 丢弃              |
| 重复 cold_start | `processDidOpen` 防 Strict Mode 双挂载                                     |
| 影响性能        | 批量 40、队列上限 300 丢最旧、10s flush、埋点失败不抛回业务                |
| 鉴权            | 无 App JWT 则 enqueue 直接丢弃；Header 带 Bearer，事件体不带 Token         |

传输：`fetch` **直连** `TRACK_BASE_URL`（不经 Node 业务信封）；成功判据为 Track `{ ok: true }`。

### 9.9 端到端数据流（摘要）

```text
业务 / TelemetryHost / crash
        │
        ▼
  enqueue（补全 event_id、上下文、sanitize props）
        │
        ▼
  MMKV telemetry:pending_v1（权威队列）
        │
        ▼
  flushPending → POST /v1/track/events
        │
        ▼
  Go Track → SQLite（events / presence / 日后聚合）
        │
        ├── heartbeat 等 → 回写 Node 在线态
        └── Admin 大屏 / 问数 ← Node BFF ← Track 查询 API
```

模块级 HOW、接口差异、实现地图见 `[自研埋点SDK一期.md](./自研埋点SDK一期.md)`；联调见 `[../联调指南-埋点.md](../联调指南-埋点.md)`。

### 9.10 后续扩展时注意

1. 新 `event_type`：先改 Track 契约与 `TRACK_EVENT_TYPES`，再改客户端。
2. 新点击：优先 `trackClick`，名称稳定、可聚合。
3. 新性能：优先 `measure*` 或显式 `perf`；注意脏样本过滤。
4. 若补曝光：需另定 RN 侧「可见」方案与阈值阈值（一期明确不做）。
5. 原生崩溃：二期议题，不在当前 SDK 范围。
