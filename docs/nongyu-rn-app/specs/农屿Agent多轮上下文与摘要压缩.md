# Spec：农屿 Agent 多轮上下文与摘要压缩

| 项       | 内容                                                                            |
| -------- | ------------------------------------------------------------------------------- |
| 应用     | `packages/nongyu-agent-sdk`（主）+ `apps/nongyu-rn-app`（接线与 Toast / 落盘）  |
| 需求类型 | **基建**                                                                        |
| PRD      | `docs/forhuman/rawprds/nongyu-rn-app/Shell/农屿Agent多轮上下文与摘要压缩PRD.md` |
| 入口     | `/ai` 发消息；SDK `Agent.complete` / `Agent.stream`                             |
| 关联     | 农屿 Agent 会话管理、`useAgentChat`、`ContextManager`、全局 Toast               |
| 状态     | **已落地（待人工回归）**                                                        |
| 技术方案 | `docs/nongyu-rn-app/tech/农屿Agent多轮上下文与摘要压缩-技术方案.md`             |

本 Spec 修正《农屿 Agent 会话管理》§3 / §5.7 中「不改 AgentLoop / 模型上下文」的边界：本期**必须**改 SDK 运行时上下文。会话抽屉、配额、UI 气泡持久化规则仍以会话管理 Spec 为准。

---

## 1. 背景

**Why**：用户能在同一会话里连续提问，但模型每次只看到当前一句，无法指代上文、无法基于上一轮工具结果追问。SDK 虽有 `ContextManager` 与 hybrid 设计，未接入 `AgentLoop`。

**What**：每次调用把当前会话的模型上下文（全量历史，或「摘要 + 近轮原文」）注入 LLM；超阈值时用同一对话模型压缩旧段；压缩成功 Toast；摘要随会话落盘。UI 仍展示完整本地消息，不因压缩删气泡。

---

## 2. 目标

1. 同一会话内第 N 句能引用第 1…N-1 句的用户原话、助手回复、工具入参与工具结果。
2. 未超阈值时：注入该会话**全部**可映射的模型消息（见 §5.2），不得只发当前 `prompt`。
3. 超阈值时：hybrid 压缩——旧段变为一条摘要，最近 **6** 轮用户对话及其间的 assistant/tool 原文保留。
4. 压缩成功：全局 Toast「当前会话过长，已做摘要压缩」。
5. 杀进程后打开同一会话：继续带上已落盘摘要 + 近轮原文，不把已压缩掉的旧原文再次全量塞进模型。
6. 切换会话 / 新对话：模型上下文互不污染（Agent 单例不得串会话）。

---

## 3. 边界（非目标）

- 设置页配置 `maxTokens` / 策略 / 摘要模型
- 独立摘要模型或第二套 API Key
- 跨会话记忆、用户长期画像、云端同步摘要
- 聊天列表插入系统气泡或「正在整理」占位
- 为压缩单独打断用户输入或取消本轮发送
- Web 管理端智慧助手（仍未接入同一 Agent）
- Tokenizer 本地精确计数（继续以接口 `usage` 为主）
- 修改欢迎语文案、会话抽屉交互、10 条 LRU 配额

| 决策     | 结论                                                                                                                   |

## 5. 详细需求

### 5.1 每次请求必须带上的模型消息

`complete` / `stream` 在调用模型前，`messages` 不得再等于「仅当前 user prompt」。

顺序固定为：

1. Agent `systemPrompt`（一条 `system`）
2. 若该会话存在有效摘要：一条额外上下文（角色实现自定，语义须标明「此前对话摘要」，不得覆盖 1 的系统人设）
3. 当前窗口内的历史：user / assistant / tool，时间顺序
4. 本轮新的 user prompt

**本轮 tool 循环**（多 step）仍把本轮新产生的 assistant `tool_calls` 与 tool 结果追加进**当次**窗口，行为与现网单轮 loop 一致。

### 5.2 UI 消息 → 模型消息映射

RN / Hook 层 `ChatMessage` 只有 `user` | `assistant`，工具在 `assistant.toolCalls` 上。

注入模型时必须展开：

| UI                               | 模型侧                                                                                                                       |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `role: user`                     | `role: user`，`content` 为用户原文                                                                                           |
| `role: assistant` 且无 toolCalls | `role: assistant`，`content` 为回复原文                                                                                      |
| `role: assistant` 且有 toolCalls | `assistant`（含 `tool_calls`）+ 每条 tool 结果一条 `role: tool`（`content` 为结果的 JSON 或字符串；须带对应 `tool_call_id`） |

排除：

- 空 assistant 占位（`pending` 且无内容、无 toolCalls）
- 欢迎语若未进入 `ChatMessage` 列表则本就不注入；若误入且可识别为欢迎语，不得当作用户历史（与会话管理 Spec 欢迎语规则一致）
- `status === "error"` 且无有效 content 的失败气泡：不注入

### 5.3 压缩触发

| 项           | 要求                                                                         |
| ------------ | ---------------------------------------------------------------------------- |
| 主信号       | 上一轮（含本会话内上一次成功的 LLM 调用）返回的 `usage.prompt_tokens`        |
| 条件         | `prompt_tokens >= 28000 * 0.8`（即 ≥ 22400）                                 |
| 流式无 usage | 允许用字符粗估（实现自定系数）代替 `prompt_tokens`；估到阈值同样触发         |
| 时机         | 在**下一次**向对话模型发起请求之前压缩；压缩完成后再带压缩后窗口请求本轮回复 |
| 不触发       | 窗口内用户轮次 ≤ 6：即使估算偏高也不裁掉唯一历史                             |

`maxTokens` / `compactThreshold` / `keepLastNTurns=6` 为 SDK 默认，本期不进设置页。`createAgent` 可覆盖，RN 使用上述默认。

### 5.4 Hybrid 压缩行为

一次成功压缩须同时满足：

1. 将「窗口中除最近 6 个 user 轮及其后伴随的 assistant/tool」之外的消息视为**旧段**。
2. 调用同一对话模型生成旧段摘要（输入 = 已有摘要（若有）+ 旧段原文）。摘要须覆盖：用户意图、关键约束、已查到的事实（成绩/课表/活动等）、未完成事项；不得把工具原始超长 JSON 整段抄进摘要。
3. 窗口替换为：摘要 + 近 6 轮原文。
4. 发出 `context:compact`（或等价回调），payload 至少含：`ok: true`、压缩前后规模（token 或消息条数）。
5. RN 收到成功信号后 Toast 固定文案：**「当前会话过长，已做摘要压缩」**（用现有 `toast()`）。
6. 将新摘要与压缩游标写入当前落盘会话。

**一轮对话只 Toast 一次**：若本轮为了回复走了多 step，压缩只允许发生在本轮**第一次**对话模型调用前；本轮后续 tool 循环不再触发第二次摘要。

### 5.5 摘要失败

摘要模型调用失败、超时、空结果、JSON/协议不可用时：

1. 仍裁掉旧段，只保留近 6 轮原文（纯 trim 降级）。
2. 本轮继续用降级后窗口请求回复，**不得**因此拒绝用户消息。
3. Toast 文案：**「会话过长，摘要失败，已仅保留最近对话」**。
4. 不把失败摘要当有效摘要落盘；游标仍更新为「旧段已丢」，避免下轮再次把已丢原文塞回模型。

### 5.6 落盘字段（会话）

在现有 `AgentChatSession` 上增加模型上下文（名称以实现为准，语义如下）：

| 字段                  | 说明                                                                                               |
| --------------------- | -------------------------------------------------------------------------------------------------- |
| `llmSummary`          | 当前有效摘要；无则省略                                                                             |
| `llmCompactedUntilId` | UI `messages` 中已被摘要/丢弃、不再注入模型的最后一条消息 id（或等价游标）。其后的消息构成近轮窗口 |

约束：

- `messages` 仍为完整 UI 历史（含已被摘要覆盖的旧气泡）。
- 读取旧版本会话（无上述字段）：视为无摘要、全量注入，直到首次触发压缩。
- 登出 / 清会话时连同摘要字段删除（沿用会话管理清除路径）。

### 5.7 会话隔离

| 事件                                  | 模型上下文                                                        |
| ------------------------------------- | ----------------------------------------------------------------- |
| 新草稿                                | 空窗口、无摘要                                                    |
| 打开历史会话                          | 加载该会话 `llmSummary` + 游标之后的 `messages` 映射              |
| 切换会话                              | 先 `stop`（已有规则），再换成目标会话上下文，禁止沿用上一会话摘要 |
| Agent 单例重建（改配置 / invalidate） | 仍按当前活跃会话的落盘字段恢复，不得串到别的学号/会话             |

`useAgentChat` 每次 `stream` 必须传入：**当前 UI 历史（不含本轮刚插入的空 assistant 占位）+ 该会话摘要/游标**。禁止依赖 Agent 进程内「上一次 run 留下的 messages」（`resetState` 现状必须改掉或改为按传入历史重建）。

### 5.8 对 `complete` 的同等要求

非流式 `complete` 与 `stream` 使用同一套组上下文 / 压缩逻辑。RN 主路径是 `stream`。

## 6. 业务流程

### 6.1 短会话续聊

1. 用户连续发送多句，总 prompt 低于阈值。
2. 每次请求携带 system + 此前全部映射消息 + 本句。
3. 无 Toast、无摘要字段。

### 6.2 首次压缩

1. 上一轮 `prompt_tokens` ≥ 22400。
2. 用户再发一句 → 先对旧段摘要 → 成功 Toast「当前会话过长，已做摘要压缩」→ 再用「摘要 + 近 6 轮 + 本句」请求回复。
3. 列表气泡仍能滚到最早的用户消息。
4. 杀进程再打开：模型侧仍是摘要 + 近轮，不是又把全部旧 JSON 打满。

### 6.3 再次压缩

1. 近轮再次涨过阈值。
2. 摘要输入 = 旧摘要 + 新裁掉的那一段，而不是整份 UI 历史。
3. 再次成功则再次 Toast（允许；用户明确要求每次触发都告知）。

### 6.4 摘要失败

1. 触发压缩但摘要调用失败。
2. Toast「会话过长，摘要失败，已仅保留最近对话」。
3. 本轮仍能回复；之后模型不再看到被裁旧段。

## 7. 验收标准与测试方案

### 7.1 功能（手动 / 联调）

- [ ] 同一会话：先说「我叫小明」，再说「我叫什么」→ 模型能答出小明（证明历史已注入）。
- [ ] 先查一次课表/二课（有工具卡片），再问「刚才那个结果里第一条是什么」→ 能依据工具结果作答，而不是声称没有上文。
- [ ] 新对话后上一会话的名字/工具结果不再被引用。
- [ ] 切换会话 A→B：B 的回复不带 A 的事实。
- [ ] 短会话无压缩 Toast。
- [ ] 人为或长对话使 `prompt_tokens` 过阈值后，下一条发送出现成功压缩 Toast，且之后回复仍连贯。
- [ ] 压缩后滚动列表仍能看到压缩前的用户气泡。
- [ ] 压缩后杀进程再进该会话，再问上文关键事实，仍能答（摘要生效）；不要求逐字复述被压缩的工具 JSON。
- [ ] 模拟摘要失败：出现失败 Toast，本轮仍有回复，且不再把失败当成功摘要。
- [ ] 本轮多 tool step 不会连续弹出多次成功压缩 Toast。

### 7.2 UI

- Toast 使用现有全局 `toast`，文案与 §5.4 / §5.5 一致；不插入聊天气泡。
- 压缩过程中输入区可保持发送中状态（`isLoading`），无需单独「压缩中」文案。

### 7.3 非功能

- 不得把其它学号会话摘要写入当前桶。
- 压缩与摘要调用失败不得导致白屏或卡死在 loading（须有超时/错误路径进入 §5.5）。
- 不新增设置项。

## 8. 实施备注（非契约）

建议落点（实现期可调整）：

- 接通 `AgentLoop.buildInitialMessages`：接受历史 + summary，而不是只 `prompt`
- 实现 `summarization` / `hybrid`（现 `compact` 的 Phase 5 空分支）
- `useAgentChat`：`agent.stream({ prompt, messages, summary })` 或等价；订阅 compact 回调
- `ai.tsx` + session repository：读写 `llmSummary` / 游标；监听 compact 打 Toast
- 流式路径尽量解析 usage；没有则粗估

SDK 已有设计参考：`packages/nongyu-agent-sdk/TECH-DESIGN.md` §5（默认 8000 以本 Spec 的 28000 为准）。
