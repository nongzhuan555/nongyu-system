# Spec：累计活跃天数与活跃排行

| 项        | 内容                                                                  |
| --------- | --------------------------------------------------------------------- |
| 应用      | `apps/nongyu-web-admin` + `apps/nongyu-node-server`                   |
| 需求类型  | **业务**                                                              |
| PRD       | `docs/forhuman/rawprds/nongyu-web-admin/累计活跃天数与活跃排行PRD.md` |
| 视觉准则  | `design-system/web-admin/MASTER.md`                                   |
| 前置 Spec | `用户管理.md`、`用户管理今日活跃筛选.md`、`数据大屏.md`               |
| 状态      | **已实现**                                                            |

---

## 1. 背景

管理员需要知道每个用户「累计活跃了多少天」，并在数据大屏看到活跃排行。现有能力只有：

- `users.last_active_at`：最近一次活跃时间（会被覆盖）
- 用户管理「仅今日活跃」筛选：按业务日过滤名单
- 大屏 DAU：Track `app_open` 去重人数（全局指标，非按人累计）

本需求在业务库落**向前累计**的活跃天数，并在用户列表 / 详情 / 数据大屏排行展示与排序。

---

## 2. 目标

1. 业务日（`BUSINESS_TZ`）内，用户经 presence / 活跃回写路径首次被记为活跃时，`active_days` **最多 +1**。
2. 管理端用户列表展示「累计活跃天数」，支持按该字段 **服务端** 升/降序（分页正确）。
3. 用户详情抽屉展示「累计活跃天数」。
4. 数据大屏新增「用户活跃排行」**水平或垂直柱状图**：默认 Top50、默认降序；可切换升序与 Top 100/200。
5. 文案标明：累计从功能上线起算，**不等同**大屏日活（DAU）口径。

---

## 3. 边界（非目标）

- 不上线前历史回填；不做 Track `events` 联查累计。
- 不要求与 Track DAU / `app_open` 名单一致。
- 不做「活跃天数区间」筛选（如 ≥7 天）；仅排序与排行。
- 不新增独立详情路由。
- 不改 RN App 上报协议（复用现有 presence → Node 回写）。
- 不做导出、不做助手 SQL 自由查本字段的强制要求（助手列表字段可顺带透出，非阻断）。

---

## 4. 详细需求

### 4.1 数据模型（Node / MySQL）

在 `users` 表新增：

| 字段                | 类型                           | 默认   | 说明                                 |
| ------------------- | ------------------------------ | ------ | ------------------------------------ |
| `active_days`       | `INT UNSIGNED NOT NULL`        | `0`    | 累计活跃天数（上线后向前累计）       |
| `active_day_bucket` | `DATE NULL` 或等价「业务日键」 | `NULL` | 最近一次已计入的业务日，用于同日去重 |

约束与行为：

- 存量行迁移后均为 `active_days=0`，`active_day_bucket=NULL`。
- 当 presence / 登录等路径更新活跃时：若当前业务日 ≠ `active_day_bucket`，则 `active_days = active_days + 1`，并写入当日 `active_day_bucket`；否则只更新 `last_active_at` / `is_online` 等既有字段。
- 业务日边界与「今日活跃」筛选一致：使用 `BUSINESS_TZ` + 既有 `businessDayUtcRange`（或同等工具）。
- 建议索引：`idx_users_active_days (active_days)`（支撑列表排序与排行查询）。

### 4.2 计数触发路径

必须覆盖所有会刷新「活跃」的正式路径，至少包括：

1. `POST /api/internal/users/presence`（Track 回写）
2. 登录成功时已有的 `last_active_at` 刷新（若存在）

同日多次心跳不得重复 +1。离线回写（`is_online=0`）若仍带有效 `last_active_at_ms`：**仍按业务日去重累计**（与「今日活跃」看 `last_active_at` 一致）；若产品后续要「仅在线心跳才算」，须另开需求。

### 4.3 用户列表 API

`GET /api/admin/users` 扩展：

**Response `list[]` 新增**

| 字段         | 类型     | 说明             |
| ------------ | -------- | ---------------- |
| `activeDays` | `number` | 累计活跃天数，≥0 |

**Query 新增**

| 参数        | 取值                 | 说明                                                                                   |
| ----------- | -------------------- | -------------------------------------------------------------------------------------- |
| `sortBy`    | 省略 \| `activeDays` | 省略：保持现有默认 `id DESC`                                                           |
| `sortOrder` | `asc` \| `desc`      | 仅当 `sortBy=activeDays` 时生效；非法值拒绝或回落（实现选一，须在错误信息/测试中固定） |

排序规则：

- `sortBy=activeDays`：`ORDER BY active_days {ASC|DESC}, id ASC`
- 与现有 `keyword` / `role` / `status` / `isOnline` / `activeToday` 筛选 **可组合**（先 WHERE，再 ORDER，再分页）

### 4.4 用户详情 API

`GET /api/admin/users/:id` 的详情对象新增 `activeDays: number`。

### 4.5 活跃排行 API（大屏）

新增（建议路径，实现时可微调但须写入接口文档）：

`GET /api/admin/dashboard/active-days-ranking`

| Query   | 取值                   | 默认   | 说明             |
| ------- | ---------------------- | ------ | ---------------- |
| `limit` | `50` \| `100` \| `200` | `50`   | Top N            |
| `order` | `asc` \| `desc`        | `desc` | 按 `active_days` |

过滤：

- `status = 1`（正常）
- `active_days > 0`

次序：`ORDER BY active_days {ASC|DESC}, id ASC`，`LIMIT N`。

**Response `data`**

```ts
{
  list: Array<{
    id: number;
    studentNo: string;
    name: string;
    activeDays: number;
  }>;
  limit: number;
  order: "asc" | "desc";
}
```

鉴权：与其它 admin dashboard 接口一致（管理员会话）。

### 4.6 Web 管理端 · 用户管理

1. 桌面表格新增列「累计活跃天数」（`activeDays`），宜靠近「在线」或「最近登录」。
2. 该列开启 Ant Design Table **服务端排序**（`sorter` + `sortOrder` 受控），切换时请求带 `sortBy`/`sortOrder`，并重置或保持页码策略与现有筛选一致（改排序回到第 1 页）。
3. 窄屏卡片列表：次要信息行可展示 `活跃 N 天`（有空间则展示；无则至少详情可见）。
4. 页头说明可补一句：累计从统计上线日起算，非历史回填、非 DAU。
5. 详情抽屉「最近活跃」旁或档案区增加「累计活跃天数」。

### 4.7 Web 管理端 · 数据大屏

1. 新卡片 `id`：`chart-active-days-ranking`（写入默认布局，靠近 `chart-user-growth`）。
2. 图表类型：柱状图；类目轴文案为 `姓名（学号）`；数值轴为累计天数。
3. 控件：
   - 升降序：复用/对齐现有 `ChartSortToggle`；**本卡默认 `desc`**（与本 Spec 一致；其它图可仍默认 desc）。
   - Top 档：`50` / `100` / `200`，默认 `50`；切换后重新请求。
4. 空数据：全员仍为 0 或过滤后为空时，展示空态文案（如「暂无累计活跃数据」），不报错。
5. 失败隔离：本卡失败不影响其它大屏卡片（与现有 Track/本库隔离一致）。
6. 标题建议：「用户活跃排行」；副文案可注明「上线后累计 · 正常账号 · 天数>0」。

### 4.8 助手（可选增强）

- `admin_users_list` 结果透出 `activeDays`；若易改则支持 `sortBy`/`sortOrder`。
- 可不新增排行 Tool（非阻断）；若加，须与 4.5 同源。

---

## 5. 业务流程

```
App 心跳/打开 → Track presence → POST /internal/users/presence
  → 计算 BUSINESS_TZ 业务日 D
  → 若 D != active_day_bucket：active_days+=1，active_day_bucket=D
  → 更新 last_active_at / is_online

管理员打开用户管理
  → GET /api/admin/users?...&sortBy=activeDays&sortOrder=desc
  → 表格展示 activeDays；点击列头切换排序

管理员打开数据大屏
  → GET /api/admin/dashboard/active-days-ranking?limit=50&order=desc
  → 柱状图渲染；切换 Top/排序再请求
```

## 6. 验收标准与测试方案

### 6.1 后端（单元/集成测试优先）

- [ ] 同业务日多次 presence：`active_days` 只 +1。
- [ ] 跨业务日两次 presence：`active_days` +2，`active_day_bucket` 为后一日。
- [ ] 列表默认排序行为不变；`sortBy=activeDays` 时分页次序正确，并列按 `id ASC`。
- [ ] 详情返回 `activeDays`。
- [ ] 排行：排除 `status=0` 与 `active_days=0`；`limit`/`order` 生效；非法 `limit` 校验失败或明确拒绝。

### 6.2 前端 · 用户管理

- [ ] 桌面表可见「累计活跃天数」列；点击可升/降序且换页后排序保持。
- [ ] 详情抽屉可见累计天数。
- [ ] 与「仅今日活跃」等筛选组合可用。

### 6.3 前端 · 数据大屏

- [ ] 出现「用户活跃排行」卡；默认 Top50 + 降序柱状图。
- [ ] 可切升序、Top100/200，图表数据随之变化。
- [ ] 类目为 `姓名（学号）`；空态与单卡失败不影响整页。

### 6.4 文案

- [ ] 列表或大屏至少一处说明：从统计上线日起累计，非历史、非 DAU。
