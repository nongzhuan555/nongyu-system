## 1. 背景

内容管理列表已返回 `viewCount`、`replyCount`，但 `GET /api/admin/posts` 固定 `ORDER BY published_at DESC`，前端表格无列头排序。管理员无法按阅读量或留言量浏览分页结果。用户管理已有 `sortBy` / `sortOrder` 先例，本需求对齐该模式。

---

## 2. 目标

1. 管理端内容列表支持按**阅读量**、**回复/留言量**服务端升/降序，分页结果全局有序。
2. 默认排序保持**发布时间降序**；取消列排序后回到该默认。
3. 三个 Tab（公告 / 反馈 / 建议）行为一致；公告「回复」列仍展示「—」，但接口层允许按 `replyCount` 排序（公告通常为 0，不单独禁用）。
4. 同步更新接口文档与前端查询类型；后端单测覆盖排序契约。

---

## 3. 边界（非目标）

- 不新增按覆盖率、`uniqueReaderCount`、作者等字段排序。
- 不改变 `viewCount` / `replyCount` 的统计与展示口径（反馈仍以「已回复/未回复」标签展示；大院仍显示「N 条留言」）。
- 不改 App 端帖子列表排序。
- 不改详情抽屉、发布/编辑/软删流程。
- 不强制改智慧助手 SQL/工具（非阻断）。
- 默认跳过独立技术方案文档；若审查后需要再补。

---

## 4. 详细需求

### 4.1 排序字段语义

| `sortBy`     | 对应数据                            | UI 列    | 说明                                                               |
| ------------ | ----------------------------------- | -------- | ------------------------------------------------------------------ |
| （缺省）     | `posts.published_at`                | 发布时间 | 默认；`sortOrder` 固定视为 `desc`（与现网一致）                    |
| `viewCount`  | `posts.view_count`                  | 阅读量   | 数值升/降序                                                        |
| `replyCount` | 未软删回复/留言条数（与现列表一致） | 回复     | 与现有 `countRepliesForPosts` 口径一致；须在 SQL 层参与 `ORDER BY` |

同时只能生效一个 `sortBy`。`sortOrder` 仅在传入 `sortBy` 时有效，取值 `asc` \| `desc`，缺省 `desc`。仅传 `sortOrder` 而无 `sortBy` → 校验失败（400，文案对齐用户列表：「sortOrder 须配合 sortBy 使用」）。

**并列次序（稳定次序）**：主排序字段相等时，次级按 `published_at DESC`，再按 `id DESC`。

### 4.2 API：`GET /api/admin/posts`

在现有 Query 上扩展：

| 参数        | 必填 | 说明                                              |
| ----------- | ---- | ------------------------------------------------- |
| `sortBy`    | 否   | `viewCount` \| `replyCount`；不传则按发布时间降序 |
| `sortOrder` | 否   | `asc` \| `desc`；仅配合 `sortBy`；默认 `desc`     |

其余 `postType` / `subtype` / `keyword` / `includeDeleted` / `page` / `pageSize` 行为不变，且与排序可组合。

**实现约束**：

- 排序必须在数据库查询中完成后再 `LIMIT/OFFSET`，禁止对当前页内存排序。
- `replyCount` 排序：用子查询或 `LEFT JOIN` 聚合未软删 `post_replies`（或项目实际表名）计数，不得先分页再补 `replyCount` 再排序。
- 响应字段不变；列表项仍返回 `viewCount`、`replyCount`。

### 4.3 前端：内容管理 `PostListPanel`

- 「阅读量」「回复」列开启 Ant Design Table `sorter`（`sortOrder` 受控）。
- 用户点击列头 → 更新 `sortBy` / `sortOrder` → **重置到第 1 页** → 重新请求列表。
- 三态：升序 → 降序 → 取消（取消后清空 `sortBy`，回到默认发布时间降序）。
- 「发布时间」列可不做 sorter（默认已是按时间）；避免与自定义 `sortBy` 双轨冲突。若实现时顺带加发布时间 sorter，仅允许映射为「无 sortBy」（desc）或显式不引入新 `sortBy` 枚举；**本 Spec 不要求**发布时间列可点。
- 切换 Tab / 变更筛选（关键词、子类型、含已删除）时：保留当前 `sortBy`/`sortOrder`，但页码重置为 1（与现有筛选重置页码策略一致；若现网筛选已重置页码则沿用）。
- 窄屏：列本身已有 `responsive` 隐藏时，不可见列无法点击属可接受；不另做工具栏排序下拉（本刀非目标）。

## 5. 业务流程

```
管理员打开内容管理 Tab
  → 默认请求：无 sortBy → published_at DESC
  → 点击「阅读量」列头
      → sortBy=viewCount, sortOrder=asc|desc（首次一般为升序，依 Ant Design 默认；再点切换）
      → page=1，带参请求 GET /api/admin/posts
  → 点击「回复」列头 → 同理 sortBy=replyCount
  → 再次点至取消 → 去掉 sortBy/sortOrder，恢复发布时间降序
```

说明：Ant Design 默认首次点击多为升序；以组件默认三态为准，不强制首次必为降序。

## 6. 验收标准与测试方案

### 6.1 后端

| 用例                                 | 期望                                                  |
| ------------------------------------ | ----------------------------------------------------- |
| 无 sort 参数                         | 与现网一致：按 `published_at DESC`                    |
| `sortBy=viewCount&sortOrder=desc`    | 全量过滤结果按阅读量降序分页；第 2 页衔接正确         |
| `sortBy=viewCount&sortOrder=asc`     | 阅读量升序                                            |
| `sortBy=replyCount&sortOrder=desc`   | 按未软删回复/留言数降序；口径与列表 `replyCount` 一致 |
| 仅 `sortOrder=desc`                  | 400，提示须配合 `sortBy`                              |
| `sortBy` 非法值                      | 400                                                   |
| 与 `keyword` / `includeDeleted` 组合 | 先过滤再排序再分页                                    |

单元/接口测试写入 `apps/nongyu-node-server/tests/`（可新建或并入既有 posts 相关测试）。

### 6.2 前端（理想操作）

1. 进入「内容管理」→ 任一 Tab：列表默认最新发布在前。
2. 点击「阅读量」列头：表头出现升/降序图标，列表按阅读量重排，翻页后顺序连续。
3. 点击「回复」列头：反馈墙「已回复」倾向聚在一端（降序时），大院高留言数靠前（降序时）。
4. 取消排序：恢复发布时间降序。
5. 排序状态下搜索关键词：结果仍按当前排序字段有序。

### 6.3 UI 描述

不新增独立控件；沿用现有表格列头排序箭头，视觉与 Ant Design / 管理端其它可排序表一致，不引入新色板或卡片。
