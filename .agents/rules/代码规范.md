# 代码规范

## 文档说明

本文件约束农屿系统**如何写代码**（风格、结构、类型、安全与可维护性）。  
工作流、门禁、SDD、Git 提交等见：

- `.agents/rules/开发规范.md`
- `.agents/rules/Git规范.md`
- `.agents/skills/sdd-guidelines/SKILL.md`

细则与示例优先落在对应 Skills；本文件只写**必须遵守的硬约束**与跨端通用原则。格式与低级风格由 `oxlint` / `oxfmt` / TypeScript 强制，本文件不重复罗列可自动修复的格式细则。

权威参考（选型对齐用，不必全文照搬）：

- TypeScript：官方 Handbook + Google TypeScript Style Guide
- React：React 官方文档 + 本仓库 `vercel-react-best-practices`/`react-native-best-practices`（React Native）
- Node：Node.js Best Practices（goldbergyoni）+ 本仓库 `nodejs-backend-patterns`
- Go：Effective Go + Uber Go Style Guide + 本仓库 `golang-*` Skills

## 一、通用规范（全栈）

### 1.1 命名

- 变量、函数、方法、参数：**camelCase**（Go 除外，见第四节）
- 类型、接口、类、枚举、组件名：**PascalCase**
- 常量：业务常量优先 `UPPER_SNAKE` 或 `as const` 对象；配置键与环境变量用 `UPPER_SNAKE`
- 文件名：与导出主体一致；React 组件文件用 PascalCase；工具/hooks 用 camelCase（如 `useUserStore.ts`）
- 布尔值用肯定语义前缀：`is` / `has` / `can` / `should`
- 命名表达**业务含义**，禁止 `data`、`info`、`temp`、`obj`、`handleClick1` 等含糊名
- 禁止拼音缩写混用；专有名词可保留（如 `OAuth`、`MySQL`）

### 1.2 注释与文档

- 函数、类、接口、复杂业务分支须有**必要的中文注释**（见开发规范）；注释解释 **Why / 约束 / 边界**，不复述代码字面意思
- 公开 API（跨包导出、HTTP 接口、SDK）须说明入参、返回、错误与副作用
- TODO/FIXME 必须带负责人或关联议题，禁止无主 TODO
- 禁止大段注释掉的死代码入库；用版本管理追溯历史

### 1.3 控制流与复杂度

- 优先**提前返回（guard clauses）**，避免深层 `if/else` 嵌套（建议视觉嵌套 ≤ 3 层）
- 复杂条件提取为命名布尔变量或小型谓词函数
- 业务逻辑四段式拆解：**数据收集 → 标准化/校验 → 逻辑判定 → 业务执行**
- 单文件建议 ≤ **700 行**；单函数建议 ≤ **50 行**（含测试可读性）；超限须拆分
- 仅为表意清晰定义中间变量，不堆砌无效临时变量

### 1.4 错误与边界

- 错误必须被处理或显式向上传递；禁止空 `catch` / 吞异常
- 对用户与调用方暴露**可行动的错误信息**；日志保留完整上下文，但不泄露密钥、token、密码
- 输入在系统边界校验（API、表单、外部回调）；内部信任已校验数据，避免重复噪声校验
- 禁止用空对象 `{}`、魔法字符串、`-1` 等模糊占位表示业务状态；用明确类型或枚举/联合类型

### 1.5 安全（基线）

- 禁止硬编码密钥、凭证、连接串；一律环境变量或密钥管理
- 外部输入默认不可信：防注入（SQL/命令/路径）、XSS、开放重定向
- 鉴权与授权在服务端强制校验；前端校验仅改善体验
- 日志与埋点脱敏：手机号、身份证、token、Cookie 不得明文落盘
- 依赖升级与已知漏洞：新增依赖须有明确用途，禁止「顺手引入」大型无关库

### 1.6 依赖与模块

- 严格遵守 monorepo 依赖策略（`docs/common/基于pnpm的monorepo项目依赖管理策略指导.md`）
- 禁止循环依赖；同一业务模块禁止混用静态 import 与动态 import（懒加载边界单独成文件）
- 修改动态导入路径后必须通过编译/类型检查，确认拆分有效
- 跨包只通过**公开导出**交互，禁止深入 `src/internal` 或相对路径穿透包边界

### 1.7 不可变与副作用

- 优先不可变数据更新；需要变更时局部、显式
- 纯计算与副作用分离：网络、IO、存储、全局状态写入集中在明确边界（service / repository / effect）
- 禁止隐式全局可变状态；确需全局状态须有单一写入路径

## 二、TypeScript 通用（前端 / Node 共享）

### 2.1 编译与类型态度

- 启用 **strict**（含 `noImplicitAny`、`strictNullChecks` 等）；项目统一 ESM（`"type": "module"` / 原生 ESM）
- **禁止 `any`**；过渡场景用 `unknown` + 收窄；第三方劣质类型用精准适配层封装，不污染业务代码
- 禁止无说明的 `@ts-ignore` / `@ts-expect-error` / `eslint-disable` 类屏蔽；必须附带原因与消除计划
- 优先 `type` / `interface` 表达领域模型；公开契约保持稳定，避免随意 `as` 断言
- 断言仅用于「编译器无法证明但运行时已保证」的窄点，且尽量紧贴校验之后

### 2.2 联合与穷尽

- 分支判断优先**可区分联合（discriminated union）**与字面量类型，禁止无约束字符串散落判定
- `switch` 处理联合类型时保持穷尽；新增成员应导致编译失败（可用 `never` 兜底检查）

### 2.3 API 与数据契约

- 跨端 DTO / 领域类型优先放共享位置，前后端禁止各写一套互不相同的「同名」模型
- 运行时校验（如 Zod）放在系统边界；校验后的类型用推断结果，避免手写重复接口
- 日期、金额、枚举在边界统一序列化约定（ISO 8601、最小货币单位等），禁止各模块私自格式化

### 2.4 异步

- 使用 `async/async`；禁止未处理的 Promise（floating promise）
- 独立异步操作用 `Promise.all` / `Promise.allSettled` 并行，避免无必要的瀑布 `await`
- 取消与超时：长耗时请求须可取消或设超时；组件卸载/请求过期后禁止再 setState

### 2.5 类与原型

- 优先函数 + 模块；需要类时用组合优于过深继承
- 禁止运行时篡改原型；测试优先实例/依赖注入式 mock，避免全局 mock 泄漏

## 三、前端（Web React / React Native）

编写与审查时同时遵循：

- `.agents/skills/vercel-react-best-practices/`（Web 性能与结构）
- `.agents/skills/react-native-best-practices/`（RN）
- `.agents/skills/tailwind-css-master/`（Tailwind，Web）
- 对应 `design-system/*/MASTER.md`（视觉与交互）

### 3.1 组件与状态

- 组件单一职责：展示 / 容器 / 钩子逻辑分离；禁止巨型「上帝组件」
- 状态就近：能用局部 state 不用全局；服务端状态与客户端 UI 状态分离
- 派生数据用计算得出，禁止同步多份会漂移的源状态
- Hooks 遵守规则：无条件调用、自定义 Hook 只封装复用逻辑并命名 `use*`
- 列表渲染稳定 `key`（业务 ID）；禁止用随机数或仅用 index（重排序场景）

### 3.2 性能（硬约束优先级）

- 消除无意义瀑布请求；独立请求并行
- 避免 barrel 导致的整包引入；重型模块懒加载
- 不为「感觉优化」默认包一层 `useMemo` / `useCallback`；按团队 React Compiler / 实测卡顿点再加
- RN：注意列表虚拟化、图片尺寸、避免在 render 中创建重对象/函数（按 RN Skill）

### 3.3 UI 与样式

- 严格遵循对应端 design-system；禁止另起一套色彩/间距/字体体系
- Web 优先 Tailwind 工具类；避免内联样式与 CSS 模块双轨并行（除非存量或特殊场景）
- 交互态完整：loading / empty / error / disabled；异步按钮防重复提交

### 3.4 前端安全与质量

- 不信任 `dangerouslySetInnerHTML` / 未消毒 Markdown；必须消毒或避免
- 路由鉴权只做体验拦截，真正权限以后端为准
- 禁止在客户端存储长期有效的明文敏感凭证

## 四、后端（Node.js + TypeScript + Express）

编写与审查时遵循 `.agents/skills/nodejs-backend-patterns/`。  
技术栈锚定：Express、mysql2、winston、pm2（见技术选型总览）。

### 4.1 分层

推荐清晰分层，禁止「路由里写 SQL + 业务规则」糊成一团：

- **Route / Controller**：解析请求、调服务、写响应
- **Service**：业务规则与事务边界
- **Repository / DAO**：SQL 与持久化
- **Middleware**：鉴权、日志、限流、错误整形

### 4.2 HTTP 与 API

- RESTful 资源语义清晰；错误响应结构统一（code / message / details）
- 入参校验在边界完成；非法输入返回 4xx，不抛未处理 500
- 鉴权中间件默认拒绝；显式放行公开路由
- 生产环境 CORS、Helmet/安全头、限流按环境配置，禁止 `origin: *` 配带凭证

### 4.3 数据与事务

- SQL 一律参数化绑定，禁止字符串拼接用户输入
- 连接池复用；禁止按请求 `createConnection` 泄漏
- 多步写操作使用事务；失败必须回滚
- Schema 变更走迁移，禁止只改库不改代码契约

### 4.4 可观测与运行

- 使用结构化日志（winston）；请求维度带 `requestId`
- 提供健康检查（liveness/readiness 按部署需要）
- 支持优雅关闭：停收新连接 → 排空 → 释放池与句柄
- 配置十二要素：环境区分 `NODE_ENV`；密钥不进仓库

### 4.5 并发与韧性

- 外部调用设超时；必要时重试仅用于幂等操作，并带退避
- CPU 密集任务勿阻塞事件循环；拆到 Worker 或独立进程
- 避免未捕获的 `unhandledRejection`；进程级监听并记录后有序退出

## 五、后端（Go）

当前仓库以 Node 服务为主；若新增 Go 服务，须遵守本节与 `.agents/skills/golang-*`（code-style / error-handling / context / security / database）。

### 5.1 风格与清晰度

- 遵循 **「Clear is better than clever」**；gofmt / goimports 为唯一格式权威
- 导出标识符须有 Go Doc 注释（以标识符名开头）
- 行宽以可读为准，过长在语义边界折行；参数过多改为 options struct
- 零值有用：`var` 表示零值意图，`:=` 用于非零初始化
- slice/map 显式初始化，避免 JSON `null` 与写 nil map panic

### 5.2 错误与 Context

- 错误用 `error` 返回，不抛 panic 做常规控制流
- 包装错误用 `%w`，保留错误链；在边界打日志，中间层少重复日志
- 每个请求传播 `context.Context`；禁止在库代码里 `context.Background()` 吞掉取消
- IO / RPC / DB 调用尊重 ctx 取消与截止时间

### 5.3 并发

- goroutine 必须可退出；禁止无泄漏保障的野 goroutine
- Channel 所有权清晰；不要用 channel 代替简单互斥
- 竞态用 `go test -race` 验证关键路径

### 5.4 安全与数据

- 参数化查询；校验边界输入
- 密钥与配置来自环境；TLS 与鉴权在网关或中间件统一处理
- 接口保持小而专注；依赖注入便于测试

## 六、测试规范（与实现同步）

- 纯逻辑、金额/权限/状态机等关键路径必须有单测；UI 以行为验收为主（见 SDD 验收约定）
- 测试名描述行为：`should_xxx_when_yyy` 或中文清晰描述均可，但同一项目内保持一致
- 单测稳定、无网络/无真实时钟依赖；时间、随机、外部服务可注入
- 禁止依赖执行顺序的脆弱测试；禁止提交 `.only` / 跳过关键用例而不说明
- 后端接口变更须同步更新契约测试或集成测试（若该模块已建立）

## 七、禁止清单（速查）

| 禁止                              | 正确做法                        |
| --------------------------------- | ------------------------------- |
| `any`、无说明的类型屏蔽           | `unknown` + 收窄；适配层封装    |
| 空 catch / 吞错误                 | 处理、转换或上抛                |
| 魔法字符串散落                    | 常量、枚举、可区分联合          |
| 路由/组件内堆 SQL 与杂乱业务      | 分层到 service / repository     |
| 拼接 SQL / 信任前端鉴权           | 参数化 + 服务端鉴权             |
| 密钥进仓库                        | 环境变量 / 密钥管理             |
| 循环依赖、跨包深路径引用          | 理顺依赖、走公开导出            |
| 巨型文件/函数硬加功能             | 先拆分再改                      |
| 用 `--no-verify` 跳过钩子常态提交 | 修到通过 lint/format/commitlint |

## 八、落地工具（与规范的关系）

| 工具                               | 职责                         |
| ---------------------------------- | ---------------------------- |
| `pnpm lint` / `lint:fix`（oxlint） | 静态质量与部分坏味道         |
| `pnpm fmt`（oxfmt）                | 格式唯一权威                 |
| `pnpm type-check`                  | 类型安全                     |
| husky + lint-staged                | commit 前硬门禁              |
| 各端 Skills + `code-reviewer`      | 架构、性能、安全的 AI Review |

格式争议以 oxfmt 结果为准；类型争议以 TypeScript strict 编译为准；业务对错以 Spec + 人工审核为准。
