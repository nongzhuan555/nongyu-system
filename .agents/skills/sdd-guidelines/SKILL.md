# SDD (规格驱动开发) 指南

规格驱动开发的核心是“规格即契约”。在编写任何实现代码之前，必须先定义清晰、可校验的规格说明。

## 何时应用

- 服务端接口开发
- Web前端、React Native前端的页面、组件、功能开发

---

## SDD 核心原则

1. **规格先行 (Spec-First)**：先写规格文档，后写业务逻辑。
2. **契约即真理 (Spec as Truth)**：规格是项目唯一的真实来源，实现必须 100% 符合规格。
3. **可校验性 (Verifiability)**：规格必须是机器可读的。
4. **关注 WHAT 而非 HOW**：规格描述系统“做什么”和“约束是什么”，而不涉及具体实现细节。（实现细节体现在代码上和某些场景下要求的实现文档或计划文档中）

---

## 工作流

### 步骤 1: 书写或读取已有的PRD

- [ ] 当被要求开发某部分功能时，先检查是否有相关的PRD，若没有，则工作流卡住，要求用户提供一份相关PRD（PRD在/docs/forhuman/rawprds目录下的对应项目目录下方检索）
      说明：不对PRD的格式和规范性做硬性要求，允许PRD看起来像草稿一样

### 步骤 2: 根据PRD编写Spec文档（AI写Spec）

- [ ] 根据PRD，编写规格文档，要求为markdown格式，内容包含以下部分：
  - 背景（why和what，这个需求是什么？为什么要做这个需求？）
  - 目标（需求要达到的目标和指标是什么？）
  - 边界（非目标，明确本次不做什么，缩小粒度，避免一次代码变更的影响范围太大）
  - 详细需求（完善PRD）
  - 业务流程
  - 验收标准和测试方案（前端代码的验收和测试给出理想的UI描述以及功能操作逻辑；后端接口的验收和测试主要依靠编写和通过单元测试）
    **注意：Spec文档的直接信息来源是需求对应的PRD，在编写Spec文档之前，需要先使用/grill-me这个Skill来要求用户澄清需求细节**
- [ ] AI先审查规格文档，确保所要求的部分都已存在，没有遗漏或错误
- [ ] 要求用户对规格文档进行审查，确认无误后，再继续下一步骤
      **注意：Spec文档的存储位置为/docs目录下对应项目的specs目录下，若无此目录需自行创建，示例为docs\nongyu-rn-app\specs**

### 步骤 3: 基于Spec文档编写技术方案文档（AI写技术方案）非必需步骤，执行前需询问用户当前需求是否需要此环节，一般简单的需求无需编写技术方案文档

- [ ] 根据规格文档，编写技术方案文档，要求为markdown文件，内容包含以下部分：
  - 技术选型（确定需要用到的依赖等等）
  - 技术方案（包括数据库设计、API 设计、前端设计等）
  - 实现步骤（包括代码实现、测试用例、部署等）
  - 注意事项（如性能优化、安全考虑等）
- [ ] AI先审查技术方案文档，确保所有需求都被覆盖，没有遗漏或错误
- [ ] 要求用户对技术方案文档进行审查，确认无误后，再继续下一步骤
      **注意：技术方案文档的编写和确定是一个需要通过和用户多轮对话讨论对齐的过程，禁止大模型盲目的、一股脑的自己编写**
      **注意：技术方案文档的存储位置为/docs目录下对应项目的tech目录下，若无此目录需自行创建，示例为docs\nongyu-rn-app\tech**

### 步骤 4: 基于技术方案和Spec文档编写实施计划（AI写实施计划）

- [ ] 根据技术方案文档和规格文档，编写实施计划，要求为markdown文件，内容包含以下部分：
  - 实施计划（包括时间表、资源分配、风险评估等）
  - 实施步骤（包括代码实现、测试用例、部署等）
  - 注意事项（如性能优化、安全考虑等）
- [ ] AI先审查实施计划文档，确保所有需求都被覆盖，没有遗漏或错误
- [ ] 要求用户对实施计划文档进行审查，确认无误后，再继续下一步骤
      **注意：实施计划文档的存储位置为/docs目录下对应项目的plans目录下，若无此目录需自行创建，示例为docs\nongyu-rn-app\plans**

### 步骤 5: 按照实施计划进行实际编码（AI写代码）

### 步骤 6: 人工Review实现代码（可审查代码或实现效果）
